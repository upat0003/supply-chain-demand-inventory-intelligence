# Data Dictionary

All tables are generated by `supply_chain/synthetic.py`, written to `data/raw/*.csv`, and loaded as bronze views by `sql/bronze/01_bronze_views.sql`. Grain is stated for each table. Types are as written to CSV; DuckDB infers types on load via `read_csv_auto`.

## products
Grain: one row per product family.

| Column | Type | Description |
|---|---|---|
| product_id | string | Unique product identifier (`PROD-0001`) |
| category | string | One of Beverages, Snacks, Dairy, Household, Personal Care, Frozen |
| subcategory | string | Category subgroup, e.g. Soft Drinks, Oral Care |
| brand | string | Synthetic brand name |
| unit_cost | decimal | Cost per unit to the retailer (AUD); a small number of rows are deliberately null - see DQ-007 |
| unit_price | decimal | Retail selling price per unit (AUD) |
| shelf_life_days | integer | Typical shelf life; short for Dairy, long for Household/Personal Care |
| is_seasonal | boolean | Whether the product has a marked seasonal demand pattern |
| launch_date | date | Date the product was first listed |
| discontinued | boolean | Whether the product is being phased out |

## skus
Grain: one row per sellable SKU (a product at a specific pack size).

| Column | Type | Description |
|---|---|---|
| sku_id | string | Unique SKU identifier (`SKU-00001`) |
| product_id | string | Foreign key to `products` |
| category / subcategory | string | Denormalised from the parent product |
| pack_size | string | e.g. `500ml`, `6x330ml`, `1kg` |
| uom | string | Unit of measure (`EA`) |
| barcode | string | Synthetic 12-digit barcode |
| unit_cost / unit_price | decimal | Pack-specific cost and price |
| case_pack_qty | integer | Units per warehouse case |
| discontinued | boolean | Inherited discontinuation flag |

## stores
Grain: one row per retail store.

| Column | Description |
|---|---|
| store_id | Unique store identifier (`STR-01`) |
| region | VIC / NSW / QLD / WA |
| warehouse_id | Foreign key to `warehouses` (servicing DC) |
| store_format | Metro / Regional / Express |
| size_sqm | Store floor area |
| open_date | Store opening date |

## warehouses
Grain: one row per distribution centre. `warehouse_id`, `region`, `warehouse_type` (National DC / Regional DC), `capacity_units`.

## suppliers
Grain: one row per supplier. `supplier_id`, `supplier_name`, `primary_category`, `region_of_origin` (including `Overseas`), `reliability_score` (0-1 latent quality driving lead-time variability), `onboarding_date`.

## daily_sales
Grain: one row per store-SKU-day. `date`, `store_id`, `sku_id`, `units_sold`, `revenue`, `promo_flag`. Contains realistic defects: ~0.25% of rows have a null `revenue` (POS extract gap, repaired in silver from unit price), a small number of exact duplicate rows (double-loaded POS batch, removed in silver), and a small number of implausible `units_sold` spikes (fat-finger entry, flagged by DQ-009 rather than silently dropped).

## inventory_snapshots
Grain: one row per location-SKU-day (subsampled to weekly cadence except for the most recent 30 days, which are kept at daily grain for operational drill-down). `date`, `location_type` (Store/Warehouse), `location_id`, `sku_id`, `on_hand_units`, `on_order_units`, `safety_stock_units`, `days_of_supply`. A small number of rows have a negative `on_hand_units` (simulated inventory-system sync defect), clipped to zero in silver and flagged via `had_negative_on_hand_defect`.

## purchase_orders
Grain: one row per purchase order line. `po_id`, `supplier_id`, `sku_id`, `warehouse_id`, `order_date`, `expected_delivery_date`, `actual_delivery_date`, `quantity_ordered`, `quantity_received`, `unit_cost`, `status` (Received/Late). Includes one deliberately injected row referencing an unknown `sku_id` (`SKU-99999`) to exercise the referential-integrity data-quality rule (DQ-006).

## lead_times
Grain: one row per supplier-SKU pair, derived from `purchase_orders`. `quoted_lead_time_days`, `observed_avg_lead_time_days`, `observed_std_lead_time_days`, `on_time_rate`, `sample_size`. Feeds the safety-stock and reorder-point calculation directly.

## promotions
Grain: one row per promotion event. `promo_id`, `sku_id`, `start_date`, `end_date`, `promo_type` (BOGO / Multi-buy / Percent Off / Feature Display), `discount_pct`, `planned_uplift_pct`.

## prices
Grain: one row per SKU per effective price change. `sku_id`, `effective_date`, `list_price`, `currency`.

## markdowns
Grain: one row per markdown event. `markdown_id`, `sku_id`, `store_id`, `date`, `markdown_pct`, `reason` (Clearance / Near-expiry / Season-end / Damaged stock).

## holidays
Grain: one row per holiday-region. `date`, `holiday_name`, `region`, `impact_level` (High/Medium/Low), used as a demand-model feature and a monitoring covariate.

## weather
Grain: one row per region-day. `date`, `region`, `avg_temp_c`, `precipitation_mm`, `severe_weather_flag`. A short run of missing `precipitation_mm` values in one region simulates a sensor outage.

## returns
Grain: one row per return line. `return_id`, `date`, `store_id`, `sku_id`, `quantity`, `reason`.

## stock_outs
Grain: one row per store-SKU-day with unmet demand. `date`, `store_id`, `sku_id`, `stockout_flag`, `lost_sales_units_estimate`, `lost_sales_revenue_estimate`.

## replenishment_decisions
Grain: one row per replenishment decision. `decision_id`, `date`, `sku_id`, `location_type`, `location_id`, `recommended_order_qty`, `reorder_point`, `safety_stock_units`, `approved_qty`, `approver`, `override_flag`, `override_reason`, `decision_status`. This is the historical planning-decision log used as the "before" baseline that the new forecasting and reorder-point models are compared against.

## Gold layer (derived)

`gold.dim_date`, `gold.dim_product`, `gold.dim_store`, `gold.dim_warehouse`, `gold.dim_supplier` are conformed dimensions. `gold.fact_daily_sales`, `gold.fact_inventory`, `gold.fact_purchase_orders`, `gold.fact_stockouts`, `gold.fact_replenishment_decisions` are the corresponding facts, plus `gold.supplier_performance`, a pre-aggregated supplier scorecard mart. See `sql/gold/01_gold_star_schema.sql` for exact column definitions and `governance/lineage.md` for column-level provenance of the metrics built on top of them.
